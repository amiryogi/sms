# Architecture proposal: one codebase, MySQL or Supabase PostgreSQL

**Status:** approved in outline on 2026-11-08 (plan review). Phases 3–7 implement it one at a
time, each reported before the next.

## Goals and non-goals

**Goals:**
- One Express API and one React frontend, with shared controllers, services, validators,
  routes, RBAC and business rules.
- One provider chosen per deployment at startup through `DATABASE_PROVIDER`.
- Existing MySQL deployments keep working with no database change: only a two-line `.env`
  change.
- Both providers maintained, with their own migration histories, and tested with the same
  integration suite.

**Non-goals:**
- No per-tenant routing: one app instance never talks to two engines.
- No Supabase Auth, no Row Level Security and no browser-to-database access; Express stays the
  only security boundary.
- No Prisma upgrade (it stays 5.22) and no frontend changes.

## Layout

```
backend/
  prisma/
    schema/
      models.prisma          ← THE source of truth: models + enums, no datasource/generator
    mysql/
      schema.prisma          ← generated by build-schemas.js (do not edit)
      migrations/            ← the existing 8 MySQL migrations, moved here unchanged
    postgresql/
      schema.prisma          ← generated by build-schemas.js (do not edit)
      migrations/0_init/     ← PostgreSQL baseline
    build-schemas.js         ← header + models → both schema files; --check for CI
    seed.js                  ← provider-neutral; uses src/database
    seeds/demoFinance.js
  scripts/
    db.js                    ← provider-aware wrapper for prisma CLI commands (guards)
    with-test-db.js          ← provider-aware test-database runner
  src/
    database/
      config.js              ← reads + validates env; fail fast; never falls back
      index.js               ← loads the matching generated client; exports { prisma, Prisma, provider, dialect, disconnect }
      dialect.js             ← the only provider-specific code (C2, C3, C4, C6, C8 helpers)
    config/database.js       ← `module.exports = require("../database").prisma` (unchanged import path for ~30 files and the unit-test mocks)
```

## Why one generated model body (and not two hand-kept schemas)

Every type and `@db` attribute in the current schema is valid on both providers (audit §2).
Only these lines differ:

```prisma
// mysql/schema.prisma (generated)
generator client { provider = "prisma-client-js"  output = "../../node_modules/.prisma-clients/mysql" }
datasource db    { provider = "mysql"       url = env("MYSQL_DATABASE_URL") }

// postgresql/schema.prisma (generated)
generator client { provider = "prisma-client-js"  output = "../../node_modules/.prisma-clients/postgresql" }
datasource db    { provider = "postgresql"  url = env("SUPABASE_DATABASE_URL")  directUrl = env("SUPABASE_DIRECT_URL") }
```

`build-schemas.js` concatenates the right header with `schema/models.prisma`.

**Alternatives considered:**

| Option | Why not |
|---|---|
| Two hand-maintained `schema.prisma` files | They drift. Every field would be edited twice, and a missed edit only shows up at runtime on one provider |
| Prisma `prismaSchemaFolder` (preview in 5.22) with shared model files | Preview feature; a shared file between two schema folders needs symlinks, which are fragile on Windows |
| One schema, provider swapped by a build step (sed on `provider =`) | One generated client at a time, so you can't build or test both from one checkout, and the migrations folder would still have to be swapped |
| A repository/ORM-agnostic layer over Prisma | Large rewrite of ~30 controllers for differences that a few dialect helpers cover |

**If a PostgreSQL-only column type is ever needed** (e.g. `citext`), `build-schemas.js` can
apply a small, explicit per-provider substitution table. This is not needed today.

## Generated clients

- **Separate clients:** each schema generates its own client with its own output folder, so
  both exist side by side and either can be loaded at runtime. `postinstall` and
  `npm run db:generate` build both. Generation needs no database.
- **Loading:** `src/database/index.js` requires only the selected client, so the other one's
  query engine is never loaded.
- **The `Prisma` namespace** (`DbNull`, `TransactionIsolationLevel`, `join`, error classes)
  comes from the active client through the database layer. Nothing imports `@prisma/client`
  directly any more.
- **`Decimal`** comes from `@prisma/client/runtime/library`, the runtime both generated
  clients use. `utils/money.js` therefore stays a pure module that unit tests load without a
  database or env.
- **Startup:** `server.js` stops creating a second `PrismaClient`; it uses the shared one and
  disconnects gracefully on `SIGTERM` / `SIGINT`.

## Configuration

| Variable | MySQL | Supabase | Notes |
|---|---|---|---|
| `DATABASE_PROVIDER` | `mysql` | `supabase` | Required; anything else stops startup |
| `MYSQL_DATABASE_URL` | required | — | `mysql://user:pass@host:3306/db` |
| `SUPABASE_DATABASE_URL` | — | required | Pooled (port 6543) + `?pgbouncer=true&sslmode=require[&connection_limit=N]` |
| `SUPABASE_DIRECT_URL` | — | required for migrations | Direct (port 5432), `?sslmode=require` |
| `MYSQL_TEST_DATABASE_URL` / `SUPABASE_TEST_DATABASE_URL` / `SUPABASE_TEST_DIRECT_URL` | tests | tests | Must differ from the configured app URLs; the test runner refuses otherwise |

**Validation in `src/database/config.js`:**
- **Provider:** it must be present and one of the two values.
- **URLs:**
  - the URL for that provider must be present;
  - its scheme must match the provider (`mysql://` versus `postgres://` / `postgresql://`);
  - a URL for the other provider that is set but unused only triggers a warning.
- **Logging:** the error message names the missing variable. URLs are never logged; only
  `host/db` is shown, never credentials.
- **Frontend:** none of these reach it. They are server-only, and Vite exposes only `VITE_*`.

## Dialect helpers (the only provider branches)

```js
// src/database/dialect.js — shape, not final code
module.exports = (provider) => ({
  text: {
    search: (v) => provider === "supabase" ? { contains: v, mode: "insensitive" } : { contains: v },
    equals: (v) => provider === "supabase" ? { equals: v, mode: "insensitive" } : { equals: v },
  },
  resetTables: (tx, names) => /* MySQL: FK checks off + TRUNCATE each; PG: TRUNCATE ... RESTART IDENTITY CASCADE */,
  isUniqueViolationOn: (err, column) => /* P2002 + target (index name or column list) mentions column */,
});
```

Controllers receive these through `require("../database").dialect`, never by testing the
provider themselves.

## Commands

| Script | Does |
|---|---|
| `npm run db:schemas` / `db:schemas:check` | Build the two schema files / fail if they are stale |
| `npm run db:generate` | Generate both clients |
| `npm run db:validate` | `prisma validate` on both schemas |
| `npm run db:migrate:deploy` | `migrate deploy` for the configured provider (using the direct URL on Supabase) |
| `npm run db:migrate:new -- <name>` | Write a new migration **for both providers** from the model change (see migration-plan.md) |
| `npm run db:status` | `migrate status` for the configured provider |
| `npm run seed` / `seed -- --reset` | Idempotent seed / wipe-and-reseed (guarded) |
| `npm run test:integration:mysql` / `:pg` | Same suites, each provider's test DB |

`scripts/db.js` prints `provider` and `host/db` before running.
- **Wrong engine:** it refuses when the URL scheme doesn't match the provider.
- **Destructive commands** (`--reset`, `migrate reset`) need `--yes-really` and are refused
  outright unless the database name ends in `_test` or the URL is one of the test URLs.

## Risks and trade-offs

- **Case-insensitive uniqueness on PostgreSQL** is enforced by the API, not the database (C3).
  This is accepted and documented.
- **Two migration histories:**
  - every schema change produces two migration files. `db:migrate:new` writes both, and CI
    checks that each history reproduces the schema;
  - hand-written data migrations (like the `fee_ledger` backfill) must be written twice.
- **Supabase free tier** pauses projects after about a week of inactivity, which affects the
  PostgreSQL test runs only. CI uses its own PostgreSQL container.
- **Two query engines in `node_modules`** add about 15 MB. Only the selected one is loaded.
- **Ordering changes (C5/C6)** touch many files, in small edits. They are verified by
  API-level ordering tests on both engines.
